# 《涌线--crowd line》游戏策划案 v0.2

**引擎：** Godot 4.7.2  
**平台：** 双端（PC + 移动端）  
**开发周期：** 2 周  
**团队：** 3 人  
**美术定位：** 整体类似 Mini Metro，三段式视野，缩小合并为“成分云”，放大可见站点细节，背景与主题随时间变化  
**核心定位：** 涌现式地铁调度沙盒，真实线网为舞台，规则驱动涌现，玩家只调参数不直接控制乘客。

## 1. 一句话概念

玩家从真实城市地铁线网中选择一张图，在限定时间内通过限流、车辆段编组、封站、跳站、广播等手段，让客流自己涌、自己堵、自己疏解，最终以积分评价经营水平。无限模式持续挑战递增难度。肉鸽机制只改参数，不改规则，涌现本质不变。

---

## 2. 核心体验

- **真实感**：线网来自真实城市，站点名称、换乘关系、线路走向有据可查。
- **涌现感**：乘客自己涌出来，拥堵自己形成，玩家只能改规则。
- **决策感**：限流还是加挂编组？封站还是广播？每个选择都有代价。**决策还带时间维度**——同样是加一节车厢，平峰做便宜又占站台少，高峰做贵且拖班次，而它买来的运力要到高峰才用得上；资源也只有一份，花了加挂就没钱救火。
- **评价感**：积分量化经营水平，可重复挑战、对比策略。
- **肉鸽感**：每局随机事件和升级，但核心涌现机制不变。
- **视野感**：缩小看整体潮汐，放大看站点细节，点击站点快速定位。
- **时间感**：昼夜交替、天气变化，画面和参数一起变，玩家不看数字就知道“要来了”。

---

## 3. 核心循环

```
观察客流 → 识别压力点 → 做出调度决策 → 系统响应 → 产生新涌现 → 再观察
```

单局时长：5—12 分钟（无限模式除外）。  
失败条件：踩踏风险、全网瘫痪、满意度归零。  
成功条件：安全、准点、吞吐量达标，积分评级。

> 目前工程里共 7 张线网、5 个池：

### 5.1 入门池（★）

**线网特征：** 1—2 条线，5—8 个站，1 个换乘站。  
**真实来源示例：** 哥本哈根 M1/M2、里斯本蓝线、成都 1 号线早期段、杭州 1 号线早期段、曼谷 BTS 素坤逸线、温州 S1/S2。  
**客流特征：** 单峰或双峰，节奏慢，异常少。  
**目标：** 积分 1000 通关，熟悉操作与涌现。  
**典型时长：** 5 分钟。

### 5.2 进阶池（★★）

**线网特征：** 3—5 条线，15—25 个站，3—5 个换乘站。  
**真实来源示例：** 新加坡 MRT 早期线网、香港荃湾线+观塘线+港岛线、台北淡水信义线+板南线、武汉 2+4 号线、成都 1/2/3 号线组合或 6 号线。  
**客流特征：** 明显早晚高峰，换乘压力大，偶发异常。  
**目标：** 8 分钟内准点率与满意度达标，积分 3000。  
**典型时长：** 8 分钟。

### 5.3 硬核池（★★★）

**线网特征：** 8 条线以上，50+ 站，10+ 换乘站，环线+放射线。  
**真实来源示例：** 重庆、北京、上海、东京、伦敦、巴黎、纽约、莫斯科地铁全网。  
**客流特征：** 潮汐流、级联延误、多线耦合、突发大客流。  
**目标：** 12 分钟内尽量不瘫痪，积分 6000。  
**典型时长：** 12 分钟。

### 5.4 无限模式

> **✅ 已实现**（`infinite_director.gd` + `Config.INFINITE`）。下面「规则」一行的"每 3 分钟"是早期目标值，
> 实际落地的节奏是 **每 75 秒一波**（`wave_seconds = 75.0`），而且每波是**加 1 站 + 1 线**而不是二选一。

**线网来源：** 从全部真实线网里随机抽一张作为起点，之后每波在已有站点附近长出新的站与线。  
**规则（实际）：** 每 75 秒一波——新增 1 站（距母站 60~130 单位抖动）＋ 1 条新线（3~5 站，相邻站间距上限 170，**线路总数上限 12**，到顶后只继续加压不再加线）；每波客流基准 ×1.09（上限 48）、随机事件与升级间隔 ×0.93（越来越密）、吞吐目标 +260、奖励 40 资源。  
**目标：** 撑到第几波就是成绩。  
**结束条件：** 只剩"撑不住"——踩踏风险、全网瘫痪、满意度归零（`_check_failure` 里用 `not infinite_mode` 直接绕开"时间到"）。  
**结算：** 除了常规五维，额外显示「撑到第 N 波 · 站点 X · 线路 Y」（`metrics.infinite/wave/stations/lines`）。  
**特色：** 每局线网不同、扩张路径不同，肉鸽升级每局不同。

> **实测**：香港图起手（2 线 18 站）跑到 291 游戏秒时已扩张到 **21 站**（3 波），
> 供参考的验收断言见 `tests/infinite_test.tscn`（新站不越界、扩张后仍全站可达、顶满 12 线上限、不看钟、普通模式不被带坏）。

## 6. 积分评价体系

### 6.1 基础指标

| 指标   | 说明                   | 权重 |
| ------ | ---------------------- | ---- |
| 准点率 | 列车到达准点比例       | 25%  |
| 满意度 | 乘客平均耐心剩余       | 25%  |
| 吞吐量 | 总运送人数             | 20%  |
| 安全分 | 无踩踏、无恐慌事件     | 20%  |
| 效率分 | 平均等待时间、换乘时间 | 10%  |

### 6.2 积分公式（示例）

```
总分 = 准点率 × 1000 + 满意度 × 1000 + 吞吐量系数 × 800 + 安全分 × 800 + 效率分 × 400
```

### 6.3 评级

| 积分      | 评级 |
| --------- | ---- |
| < 1000    | D    |
| 1000—2999 | C    |
| 3000—4999 | B    |
| 5000—6999 | A    |
| ≥ 7000    | S    |

### 6.4 结算展示

- 积分明细
- 拥堵热力图回放
- 关键时刻标记（最大拥堵、最佳决策、失误点）
- 与历史最佳对比

## 7. 肉鸽机制（不偏离涌现本质）

### 7.1 原则

- 肉鸽只改变**规则和参数**，不直接改变客流结果。
- 玩家不能直接生成或删除乘客。
- 所有随机事件都通过反馈循环影响涌现。

### 7.2 每局随机

- **线网变体**：同一城市不同线路组合。
- **初始事件**：开局随机 1 个正面 + 1 个负面。
- **升级选择**：每 2 分钟三选一。
- **异常事件**：随机时间触发。

### 7.3 升级示例

| 升级     | 效果              | 代价          |
| -------- | ----------------- | ------------- |
| 快速闸机 | 进站速度 +20%     | 满意度 -5%    |
| 智能广播 | 乘客改道概率 +15% | 冷却 +30s     |
| 检修车间 | 加挂费用 -30%，占站台时长 -20% | 初始资源 -20% |
| 宽敞站台 | 站台容量 +25%     | 建设时间 +10s |
| 应急通道 | 封站副作用 -50%   | 限流效果 -10% |

### 7.4 随机事件示例

| 事件       | 效果                     |
| ---------- | ------------------------ |
| 演唱会散场 | 某站短时大客流           |
| 暴雨       | 整体需求 +20%，速度 -10% |
| 信号故障   | 某线延误传播             |
| 出口关闭   | 某站容量 -30%            |
| 票价优惠   | 需求 +15%，持续 1 分钟   |
| 设备检修   | 某站闸机 -50%            |

## 8. 游戏对象与玩家操作

### 乘客 Agent

每个乘客只有简单规则：去目的地、选最短路径、避开拥挤、跟人走、耐心有限、从众/恐慌。  
属性：起点、终点、耐心、速度、从众性、信息获取。

### 地铁列车

编组节数（决定定员）、班次间隔、速度、延误传播。一条线晚点可能波及换乘站。运力不靠"多买车"，而靠**送车进车辆段加长编组**（详见下文「车辆段与编组延长」）。

### 站点

闸机、站台、换乘通道、出入口。每个站点有容量上限和密度阈值。

### 玩家操作

| 操作     | 代码 id         | 效果                              | 成本                     |
| -------- | --------------- | --------------------------------- | ------------------------ |
| 限流     | `limit`         | 降低该站进站速率 30s              | 15 资源；站内乘客耐心下降 |
| 升级车辆 | `upgrade_train` | 建车辆段 / 下达加挂指令（就地加长编组） | 资源（随客流高峰上浮）；加挂时该车多停 5~12s |
| 跳站     | `skip`          | 该线列车通过该站不停 20s          | 12 资源；该站乘客继续积压 |
| 封站     | `close`         | 强制改变人流 20s                  | 12 资源；满意度大降、乘客耐心大跌 |
| 广播     | `broadcast`     | 安抚恐慌 + 引导改道               | 20 资源；冷却 30s        |

> **⚠ 此次修订下线了「加车」。** 原「加车」直接凭空生成一列新车、成本固定，收益即时且可无限叠加——
> 只要资源够就能一直刷运力，玩家的决策因此退化成"点按钮"。
> 现在**运力增长必须走车辆段这条路**。
>
> **⚠ 本次修订（续）下线了「整列下线编组」。** 上一版把整列车抽进车辆段 24 秒，
> 实测代价过大：台北两条线各只有 2 列车，抽走 1 列等于该线运力腰斩、班次从 12s 翻到 25s，
> 满意度掉 0.16，而收益要等出段才兑现——结果是**理性玩家永远不会点这个按钮**。
> 现在改成"就地加挂"：车不出线路，代价从"运力腰斩 24 秒"变成"占站台 5~12 秒"，
> 并把价格与耗时一起绑到客流负荷上——于是它从一个不该点的按钮，变成一件**该挑时候做的事**。
>
> **⚠ 同时给所有操作上了价。** 原来资源只能花在车辆段上（其余操作免费），
> 于是"建了段"和"没建段"跑出**逐位相同的成绩**——钱是白送的，没有第二个出口。
> 现在 `OPERATION_COST`（15/12/12/20）让限流、封站、跳站、广播都要花钱，
> 资源第一次有了真实的机会成本。

### 车辆段与编组延长（核心运力机制）

**一句话**：想要更多运力，得挑一个**平峰**，让线路上某一列车在段站多停几秒，挂上一节车厢。

- **每线一个车辆段**，位置优先取线网 JSON 的 `depot_station`；没声明就自动选**离线路中点最近的非换乘站**
  （换乘站是要塞，不该再往上堆车辆段）。渲染为线路色棚位；未建时是灰色规划虚框。
- **两步操作**（同一个按钮，按状态自动切换语义）：
  1. **建段**：第一次对某线点"升级车辆"，先花资源把车辆段建起来（一次性）。
  2. **下单**：之后再点，**下达一张加挂指令**（段站会出现黄色脉冲环，表示有活等着）。
- **兑现**：线路上**下一列停靠段站的列车**就地加长——不需要谁被抽走。
  列车只是在该站多停 `couple_dwell` 秒（平峰 5s / 高峰 12s），**期间照常开门上下客、照常运营**。
- **完工**：该车 +1 节，**定员 = 节数 × 每节定员**
  （初始 2 节 = 80 人，与原始定员一致；上限 6 节 = 240 人），黄色进度环走满即生效。
  车一直在线上跑，车队规模从头到尾不变。
- **费用递增**：同一条线每加挂一次，下一次更贵——逼玩家在"哪条线值得投"上做取舍。
- **同时只有一张未兑现的指令**；段站有指令时按钮会提示"待加挂（等车停靠）"。
- **"分时规划"就落在这里**：加挂的**价格与耗时都随客流负荷浮动**——
  平峰 ×0.75 价格 / 占站台 5s，高峰 ×1.35 价格 / 占站台 12s。
  同一件事，在平峰做比在高峰做更便宜、占站台更短；而它买来的定员，恰恰要在高峰才用得上。
  **正确打法：平峰下手，高峰收获。**

| 参数（`Config.DEPOT`）   | 默认值    | 含义                                                     |
| ------------------------ | --------- | -------------------------------------------------------- |
| `build_cost`             | 55        | 建车辆段的一次性费用（会先乘分时系数）                   |
| `base_cost`              | 40        | 首次加挂费用（同样乘分时系数）                           |
| `cost_growth`            | 0.55      | 该线每多加挂一次，费用 ×(1 + 次数 × 该值)                |
| `couple_dwell_flat`      | 5.0       | 平峰时加挂占用的站台秒数                                 |
| `couple_dwell_peak`      | 12.0      | 高峰时加挂占用的站台秒数                                 |
| `cost_flat`              | 0.75      | 平峰价格系数                                             |
| `cost_peak`              | 1.35      | 高峰价格系数                                             |
| `load_low` / `load_high` | 0.5 / 2.0 | 客流负荷（时刻需求 × 天气）映射到 0..1 的区间            |
| `car_capacity`           | 40        | 每节车厢定员                                             |
| `min_cars` / `max_cars`  | 2 / 6     | 初始编组节数 / 编组上限                                  |
| `cars_per_upgrade`       | 1         | 每次延长几节                                             |

> 相关肉鸽升级：**检修车间**（`depot_shop`）——加挂费用 -30%、占站台时长 -20%。
> 另设 `Config.OPERATION_COST`（`limit` 15 / `close` 12 / `skip` 12 / `broadcast` 20）——
> 资源从此有多个出口，玩家必须权衡"花钱加挂"还是"花钱救火"。

#### 实测（`tests/depot_bench.tscn`，同种子 20261021，整治前 → 整治后）

| 场景 / 策略                 | 总分        | 服务人数    | 满意度      | 峰值密度    |
| --------------------------- | ----------- | ----------- | ----------- | ----------- |
| 温州·入门 / 不动手          | 3748 → 3748 | 978 → 978   | .81 → .81   | .217 → .217 |
| 温州·入门 / 有钱就点        | 3679 → 3707 | 974 → 976   | .75 → .78   | .225 → .225 |
| 里斯本·入门 / 不动手        | 3638 → 3638 | 1219 → 1219 | .77 → .77   | .285 → .285 |
| 里斯本·入门 / 有钱就点      | 3598 → 3614 | 1223 → 1226 | .74 → .74   | .350 → .342 |
| 台北·进阶 / 不动手          | 3641 → 3641 | 2613 → 2613 | .74 → .74   | .358 → .358 |
| 台北·进阶 / 有钱就点        | 3414 → 3616 | 2567 → 2622 | .58 → **.72** | .589 → **.416** |
| 重庆·硬核 / 有钱就点        | 2246 → 2834 | 431 → **4645** | — → .75     | — → 1.019   |
| （重庆·硬核 / 有钱就点 存活） | 60.5s → **385.7s** | | | |

补充两组只用来对照的：温州·入门 / 只挑非高峰 `3724`、温州·入门 / 晚出手 `3742`；里斯本与台北的"只挑非高峰"与"有钱就点"结果逐位相同。

四条结论：

1. **不改默认玩法**：`不动手` 三种线网的成绩与改造前**逐位相同**（3748 / 3638 / 3641），
   说明这轮改造没有副作用。
2. **按钮不再"绝不能点"**：台北原本点一次就满意度掉 0.16、峰值密度冲 0.589；
   现在满意度反而升到 0.72、峰值密度降到 0.416。重庆硬核从"点一下 60 秒暴毙、只服务 431 人"
   变成"活到 385.7 秒、服务 4645 人"。
3. **它仍然不是无脑最优**：轻载线网上（温州、里斯本）"有钱就点"依旧比不动手低 24—41 分——
   没拥堵时，多停的几秒就是净成本。而越晚出手、越贴着平峰出手，成绩越好
   （温州：晚出手 3742 / 只挑非高峰 3724 / 有钱就点 3707）。
   **这正是我们想要的：这是一个需要挑时机的按钮，不是一台印钞机。**
4. **再也没有乘客被赶下车**：所有实测组合里 `单次最大卸客 = 0 人`、`累计卸客 = 0 人`
   （旧版把整列车抽走时，这个数字是 30~112 人/次、累计 42~112 人）。
   加挂时列车照常开门，车厢里的人一个都不用下车——"变强"不再需要拿乘客的行程当燃料。
5. **列车加减速曲线落地后重新基线**（`Config.train_speed_factor()`）：它改变的是列车在段内的
   **速度分布**（出站加速、进站减速），按 `∫dp/v = 1` 做了时间精确归一化，所以**不是纯视觉参数**——
   它会扰动排队与扎堆的动力学。参数取激进档（`0.28/0.32/0.42`）时，温州 none `3748→3705`、
   台北 none `3641→3595`；调温和（`0.12/0.30/0.62`）后回到 `3754 / 3642 / 3649`、
   重庆 none `348.2s`（原 `350.0s`）——**全部落在 ±0.5% 内**。
   **硬核池对扰动混沌敏感**，它的单局成败（350s 上下失败）会随任何微小改动跳变，
   不要用它判读这类改动。新基线已存 `tests/bench_final.txt`。
6. **天气自然轮替落地后再次基线**：天气开始每 70~150 秒按权重轮替（开局只从"晴/阴"里抽），
   随机流与需求曲线都变了，全线数值小幅漂移（温州 none `3754→3743`、里斯本 `3649→3702`、
   台北 `3642→3618`）。**有意思的是硬核池**：重庆 none 在 `381.5s` 失败，而"有钱就点"（建车辆段）
   这次**跑满 720 秒、总分 3603**——天气带来的额外压力，反而让"提前加运力"这条策略第一次明显胜出。
   但硬核结局对随机流极其敏感，单次结果只能当"这一次"看，不要当稳定结论。
7. **硬核难度重调（用户："硬核放着不动也随便通关"）**：先只把倍率 `1.6→2.2`，结果重庆硬核
   **61.6 秒就崩**、完全没法玩；回调到 `1.8` 后重庆正常（不动手 `150s` 失败、建车辆段撑到 `340s`），
   但**温州硬核放着不动照样跑满 720 秒拿 B**。根因是**基准客流按地图站数算**
   （`clampf(站数*0.5, 2, 12)`），小地图的**绝对**客流太低——光调倍率只会把小图大图一起推爆。
   于是加了硬核专属的**绝对客流下限** `HARDCORE_MIN_SPAWN = 9.5`（人/秒）。
   新基线（`tests/bench_final.txt`，种子 20261021）：
   - 温州硬核：**不动手 `386.5s` 失败**，建车辆段**跑满 720s、总分 3637**；
   - 重庆硬核：不动手 `150.0s` 失败，建车辆段 `340.0s` 失败。
   也就是"**不动手必崩、肯投入能撑住**"这个形状终于对了——这才是硬核该有的取舍。

## 9. 涌现从哪来

- 乘客避拥挤 → 人流转向 → 新拥堵点。
- 列车延误 → 站台积压 → 换乘通道堵塞 → 级联失效。
- 从众/恐慌 → 局部密度突变 → 踩踏风险。
- 玩家限流 → 站外排队 → 需求转移 → 邻站爆满。
- 时间与天气变化 → 需求结构改变 → 旧策略失效 → 新涌现。

这些都不是脚本，是规则互动的结果。

## 10. 时间变化系统

时间不是背景板，是**涌现的驱动参数**。一局 5—12 分钟映射游戏内一天 24 小时，昼夜、天气、主题氛围同步变化。

### 10.1 昼夜循环

| 现实时长 | 游戏内时间 | 典型场景           |
| -------- | ---------- | ------------------ |
| 1 分钟   | 2 小时     | 早高峰 7:00—9:00   |
| 1 分钟   | 2 小时     | 平峰 9:00—11:00    |
| 1 分钟   | 2 小时     | 午间 11:00—13:00   |
| 1 分钟   | 2 小时     | 晚高峰 17:00—19:00 |
| 1 分钟   | 2 小时     | 夜间 19:00—23:00   |

**视觉表现：**

| 时段         | 背景色           | 线路色 | 乘客颜色       | 整体氛围   |
| ------------ | ---------------- | ------ | -------------- | ---------- |
| 清晨 5—7     | 深蓝紫 #1a1a3e   | 低饱和 | 稀疏，偏绿     | 安静，冷   |
| 早高峰 7—9   | 暖橙渐变 #2e1a1a | 高饱和 | 密集，黄红增多 | 紧张，暖   |
| 平峰 9—11    | 浅灰蓝 #1e2a3e   | 中饱和 | 稀疏，绿       | 平静，中性 |
| 午间 11—13   | 明亮蓝 #1a2a3e   | 中饱和 | 中等，绿黄     | 轻松，亮   |
| 晚高峰 17—19 | 暖红渐变 #3e1a1a | 高饱和 | 密集，红紫     | 高压，热   |
| 夜间 19—23   | 深蓝黑 #0e0e1e   | 低饱和 | 稀疏，暗绿     | 疲惫，冷   |

**过渡方式：** 着色器渐变，每 10 秒微调色温，玩家不会突然发现“天亮了”，但回头一看氛围已变。

**乘客行为随时间变化：**

- 早高峰：目的地集中在商业区/换乘站，耐心低，从众高。
- 平峰：目的地分散，耐心高，从众低。
- 晚高峰：反向潮汐，疲惫值高，恐慌阈值低。
- 夜间：班次减少，乘客少但等车久，满意度下降快。

### 10.2 天气系统

天气直接改参数，与昼夜叠加。

| 天气 | 视觉                     | 参数影响                       | 出现时段 |
| ---- | ------------------------ | ------------------------------ | -------- |
| 晴   | 干净背景，无粒子         | 基准                           | 全天     |
| 阴   | 灰色调，低对比           | 需求 -5%                       | 全天     |
| 小雨 | 细密斜线粒子，地面反光   | 需求 +10%，速度 -5%            | 全天     |
| 暴雨 | 密集粒子，屏幕水痕，雷鸣 | 需求 +20%，速度 -10%，故障率 + | 夏秋     |
| 雪   | 白色粒子，慢速飘落       | 需求 -10%，速度 -15%           | 冬       |
| 雾   | 低透明度，远景模糊       | 速度 -10%，能见度低            | 晨       |

**叠加效果：** 晚高峰 + 暴雨 = 压力翻倍，画面偏红紫，警报频繁。这是“涌”最猛的组合。

### 10.3 主题氛围

**背景元素：**

- **远景云层**：白天薄云，傍晚火烧云，夜间星空/城市灯光。
- **城市剪影**：随昼夜亮灯率变化，早高峰写字楼亮，夜间住宅区亮。
- **地标**：根据所选线路城市，背景出现地标剪影，如重庆的穿楼、跨江大桥，香港的维多利亚港，北京的故宫角楼。
- **线路特征**：重庆的穿楼站点在近景下可以看到楼中站台；跨江段背景出现江面倒影。

**UI 风格：**

- 早高峰：UI 边缘泛暖光，警报色偏橙红。
- 平峰：UI 干净，低饱和。
- 晚高峰：UI 边缘泛红光，按钮冷却环更醒目。
- 夜间：UI 暗色，霓虹描边更亮。

**音效基调：**

- 清晨：稀疏鸟鸣、远处列车声。
- 早高峰：密集脚步声、广播、闸机滴滴。
- 平峰：轻松环境音，偶尔广播。
- 晚高峰：人群嘈杂、警报、心跳。
- 夜间：空旷回声、低频轰鸣、偶尔广播。

### 10.4 时间与涌现的关系

- 早高峰：需求集中，换乘站压力大，容易涌。
- 平峰：需求分散，玩家可以喘口气，调整策略。
- 晚高峰：反向潮汐，之前管用的策略可能失效。
- 夜间：班次少，一辆车晚点影响更大，容错率低。
- 天气叠加：暴雨+晚高峰，系统逼近临界，一次小故障就可能级联。

**玩家感受：** 不用看时钟，光看画面和听声音就知道“要来了”。时间变化本身就是反馈的一部分。

### 10.5 实现方式

**着色器：**

- 全局色调映射：`uniform float time_of_day`，驱动背景色、线路色、UI 色调。
- 天气粒子：GPU 粒子系统，参数由 `WeatherSystem` 控制。
- 背景渐变：全屏 quad，用噪声+渐变生成天空/城市剪影。
- 过渡：所有参数用 `lerp` 平滑，避免突变。

**数据结构：**

```gdscript
# TimeSystem.gd
var game_hour: float = 7.0
var time_speed: float = 2.0  # 游戏内小时/分钟
var weather: String = "clear"
var weather_intensity: float = 0.0

func _process(delta):
    game_hour += time_speed * delta / 60.0
    if game_hour >= 24.0:
        game_hour -= 24.0
    update_visuals()
    update_passenger_params()
```

**接口：**

- `TimeSystem.get_hour()` → 当前游戏内小时
- `TimeSystem.get_period()` → `morning_peak` / `flat` / `evening_peak` / `night`
- `TimeSystem.get_weather()` → 当前天气
- `TimeSystem.get_demand_multiplier()` → 需求乘数
- `TimeSystem.get_speed_multiplier()` → 速度乘数

## 11. 三段式视野与成分云

### 11.1 三段式视野

| 视野层级     | 触发方式                 | 画面表现                                             | 玩家用途             | 状态     |
| ------------ | ------------------------ | ---------------------------------------------------- | -------------------- | -------- |
| 远景（云层） | 滚轮往外拉到最远         | 乘客合并为“成分云”，用颜色和密度表示客流构成         | 看全网潮汐、区域压力 | 已实现   |
| 中景（默认） | 滚轮停在中间档           | 类似 Mini Metro，乘客为小圆点，线路和站点清晰        | 日常调度、观察拥堵   | 已实现   |
| 近景（站点） | 继续往里推               | 乘客点摊开，可见单个人、耐心环、列车车厢数           | 精细调度、应急决策   | 部分实现 |

**实际实现方式（与旧文档的差异）**：三档不是写死的缩放值，而是**按当前地图几何动态计算**：

- 全貌档：把整张图正好装进视口（留 15% 边距）；
- 中景档：视口宽度约容纳 4 条平均边长的线路；
- 近景档：约容纳 1.4 条平均边长。
- 三档之间强制至少相差 1.3 倍，避免小地图上三档挤在一起。
- **有弹性**：滚轮可以越过两端（全貌能更远、近景能更近）；**手一停（约 0.3 秒）会自动回弹到最近的档位**。
  这样玩家总能"回到"一个稳定的观察档，而临时越界仍被允许。
- 相机静止在某档时，站点圆环由空心变实心（`○ → ●`），提示"现在是稳定档位"。

### 11.2 成分云

- 远景下，大量乘客不再单独渲染，而是合并为半透明色块。
- 颜色表示乘客状态构成：绿=正常、黄=等待、红=拥堵、紫=恐慌。
- 密度越高，云越浓；颜色越偏红紫，压力越大。
- **实现细节**：一朵云 = 该站四种状态各画一团软斑，按黄金角错开、面积随该状态人数占比变化，
  外圈加一圈白色描边，恐慌状态额外加一圈紫环。远景段热力图同步淡出，避免和云打架。
- **云↔点的切换由相机档位驱动**（旧文档写的"缩放 < 0.6"已失效）：
  在"全貌档 → 中景档"之间线性交叉淡化，点慢慢"析出"、云慢慢散开。
- 云会缓慢流动，方向表示人群移动趋势。——**未实现（预期）**
- 鼠标悬停或点击云，可以显示该区域客流构成饼图。——**未实现（预期）**

### 11.3 缩放与衔接动画

- **PC：** 鼠标滚轮缩放。——**已实现**（以鼠标位置为锚点，缩放不漂移）
- **移动端：** 屏幕右侧上下拖动激活式 UI 缩放。——**未实现（预期）**
- **点击站点：** 快速进入该站点近景视野。——**未实现（预期）**；当前点击只是选中站点
- **衔接动画：** 缩小/放大时云与点之间用**约 0.3 秒的交叉淡化**过渡，而不是粒子。——**已实现**
  - 旧设想"云与小圆点之间用粒子过渡"**未实现**，改为成本更低的透明度交叉淡化。
  - 近景档额外补充：乘客点散开半径变大、单个乘客画出**耐心环**（耐心越低环越短）。

## 12. 美术风格与着色器

### 12.1 定位

整体类似 Mini Metro：极简几何、干净线条、低饱和背景、高饱和线路。加入三段式视野、成分云和时间变化。

### 12.2 统一规范

> **⚠ 本节已按当前实现改写。** 原稿写的是"深灰/深蓝基底 + 半透明深色面板 + 霓虹描边"，
> 实际已整体转成 **Mini Metro 式亮色"纸面"**：奶油/浅蓝底、白色卡片、深藏青字、饱和线路。
> 理由是用户明确要求"游戏背景多亮色（类似 mini metro 那样），画面简约，但各图标能在需要时看清"。

- **背景**：亮色"纸面"——上下渐变 + 极淡点阵网格（随相机轻微反向平移制造视差）+ 缓慢漂移的大尺度光泽 + 四周收边暗角，整体色调随时段走（`shaders/bg_paper.gdshader` + `config.gd` 的亮色调色板）。
- **线路**：高饱和（青、品红、黄、绿），随昼夜微调饱和度。
- **乘客**：小圆点，颜色表示状态（绿=正常 `#4ade80`、黄=等待 `#ffd23f`、红=拥堵 `#ff5c5c`、紫=恐慌 `#c084fc`）。
  **注意 `Config.ink(c, amount)` 的 `amount` 是"往墨色 `#182236` 里兑多少"**：云用 0.18~0.30 求淡雅，
  但乘客点是画面主体，只兑 0.08，否则黄会变成橄榄、绿会发灰。
- **站点**：深藏青圆环 + 白色圆心，环大小表示容量；换乘站加亮。
- **热力图**：绿→黄→红→白。
- **成分云**：半透明色块，四种乘客状态各一团软斑（黄金角错开），密度表示压力。
- **UI**：**白色半透明卡片（`rgba(1,1,1,0.93)`）+ 细描边 + 柔和投影**，文字用深藏青。
  界面本体在 `scenes/hud.tscn` 等真实场景里，可在编辑器里直接预览与拖拽。
- **图标**：`assets/icons/` 共 22 个（操作栏 5 个、时间控制 3 个、评级徽章 5 个、列车/乘客点/站点环、天气 4 个）。
  **图标原图是"白底透明"**（图标总览本身也是白底透明图，必须先合成到深底才看得见），
  所以用在浅色按钮上时必须靠 `Button/colors/icon_*_color` 染色，否则白图标会消失。

### 12.3 着色器实现

> **⚠ 本节原文是一张愿望清单，没有区分"已做"和"计划"。** 下面是当前实际状态。

**已实现（3 个 `canvas_item` 着色器）：**

- `shaders/bg_paper.gdshader` —— 亮色纸面：渐变底色 + 点阵网格（`TIME` 驱动缓慢漂移 + `cam_offset` 视差）+ 斜向光泽 + 收边暗角。uniform：`top_color` / `bottom_color` / `grid_color` / `grid_alpha` / `grid_step` / `cam_offset` / `mood` / `drift`。
- `shaders/passenger_dot.gdshader` —— 乘客点：软芯呼吸（`breath`）+ 从中心向外扩散后淡掉的涟漪环（`pulse`/`ring`）。**相位 `phase = (VERTEX.x + VERTEX.y) * 0.04` 由点在世界里的位置推出，所以同屏的点不会齐刷刷一起闪。** 由 `passenger_layer.gd` 把材质挂在**整层** `CanvasItem` 上——`_draw()` 里单次 `draw_*` 是没法各带材质的，但整层的材质会作用于该层每一次绘制，所以逐点的 `UV`/`COLOR`/`VERTEX` 仍然独立。
- `shaders/train_body.gdshader` —— 列车车身：车窗灯带随车速滚动（越快越快）、进站前车头灯亮、减速时车尾刹车灯红、停站整体压暗半档。**逐车的"车速 / 正在减速 / 停站剩余"通过逐顶点 `COLOR.rgb` 三个通道传进来**，所以一条线一个材质就够，不必每辆车一个材质。由 `line_train_view.gd` 的 `material` + `draw_texture_rect(..., Color(spd, brake, dwell, 1))` 驱动。

**仍未做（原清单里的其余项）：**

- 密度场热力图、流线/方向场、实例化乘客（`MultiMesh`）、成分云的低分辨率密度纹理 + 模糊
- 云↔点之间的粒子过渡
- 全局色调映射、Bloom / 色差 / 径向模糊、历史帧反馈（拖尾、潮汐）
- 天气粒子目前是 CPU `_draw`（`weather_particles.gd`），未用着色器

### 12.4 音效

- 人群声随密度升高
- 警报、广播、心跳
- 异常触发时音效突变
- 缩放时音效随视野变化：远景低沉，近景清晰
- 时间变化时音效基调改变（见 10.3）

## 15. 游戏场景样例阐释

### 场景 1：入门池——温州 S1/S2

一条线，7 个站，无换乘。5 分钟，清晨发车，平峰，晴朗，画面干净。中段进入早高峰，暖色，客流增多，玩家第一次感到“涌”。结尾回到平峰，玩家松口气。玩家操作限流、升级车辆（先在平峰把编组做掉，高峰才有余量）。目标积分 1000。教学重点：理解乘客自己涌、热力图、基本操作与车辆段。

### 场景 2：进阶池——香港荃湾线 + 观塘线

两条线，18 个站，2 个换乘站（太子、旺角）。8 分钟，晚高峰 + 小雨，画面偏红，地面反光。换乘站压力大，广播引导成为关键。夜间雨停，客流减少，但班次也减少。玩家操作限流、升级车辆、跳站、广播。目标积分 3000。教学重点：换乘压力、级联延误、广播引导、资源在两条线之间怎么分配。

### 场景 3：硬核池——重庆地铁全网

20+ 条线，50+ 换乘站。12 分钟，早高峰 + 暴雨，穿楼站点近景可见楼中站台，跨江段江面倒影。画面偏红紫，Bloom 频繁，警报不断。夜间转入平峰，但故障遗留，玩家需要收尾。玩家操作全部，多线协同。目标积分 6000，不瘫痪。教学重点：级联失效、多线耦合、资源分配。

### 场景 4：无限模式——随机组合线网

从真实线网随机抽取 2 条线开始，每 3 分钟新增 1 条。无上限，时间循环加速，每 3 分钟过完一天。天气随机，昼夜交替，线网扩展。每 2 分钟随机 1 个事件。玩家操作全部，加肉鸽升级。目标存活尽可能久。教学重点：适应、取舍、长期规划。**注意**：线越加越多，而车辆段编组是每线独立且费用递增的——越到后期越要学会"放弃哪条线"。

### 场景 5：异常爆发——东京 Metro 新宿站

新宿站为核心，多条线交汇。3 分钟短局，夜间 + 演唱会散场 + 暴雨。画面从深蓝黑瞬间转红紫，Bloom 炸开。时间压力极强，玩家必须在 3 分钟内稳住。玩家操作限流、封站、广播；**升级车辆在这种短局里来不及做**——这也是"分时规划"的反面教材。目标避免踩踏，积分 2000。教学重点：应急决策、恐慌传播、从众行为。

## 20. 风险与对策

| 风险                 | 对策                                      |
| -------------------- | ----------------------------------------- |
| 真实线网数据整理耗时 | 先做 1—2 个城市，其余用程序化生成         |
| 模拟性能不足         | 低分辨率模拟，GPU 实例化，限制 Agent 数量 |
| 涌现不明显           | 调参：增强反馈循环，提高阈值敏感度        |
| 美术不统一           | 先定色板和线条规范，所有素材按规范        |
| 两周做不完           | 砍内容：先保证入门池可玩，再扩展          |
| 肉鸽偏离涌现         | 升级和事件只改参数，不改规则结构          |
| 双端缩放体验不一致   | 先做 PC，移动端用同一套视野系统，UI 适配  |
| 成分云性能开销       | 用低分辨率密度纹理 + 模糊，GPU 渲染       |
| 时间系统增加复杂度   | 先做昼夜色调，天气后置；接口提前约定      |

## 21. 一句话总结

**真实线网为舞台，三种难度池 + 无限模式，限时经营 + 积分评价，肉鸽只改参数不改规则；乘客自己涌，玩家只调规则，三段式视野从成分云到站点细节，昼夜天气驱动涌现，着色器负责视觉爆发，三人两周并行开发，先跑通入门池再扩展。**
