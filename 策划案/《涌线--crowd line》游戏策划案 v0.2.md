# 《涌线--crowd line》游戏策划案 v0.2

**引擎：** Godot 4.7.2  
**平台：** 双端（PC + 移动端）  
**开发周期：** 2 周  
**团队：** 3 人  
**美术定位：** 整体类似 Mini Metro，三段式视野，缩小合并为“成分云”，放大可见站点细节，背景与主题随时间变化  
**核心定位：** 涌现式地铁调度沙盒，真实线网为舞台，规则驱动涌现，玩家只调参数不直接控制乘客。

---

## 版本更新说明（v0.1 → v0.2）

- 新增**时间变化系统**：昼夜循环、天气系统、主题氛围。
- 时间作为涌现驱动参数，直接影响需求、速度、恐慌阈值。
- 场景样例加入昼夜与天气描述。
- 美术规范、技术架构、开发任务、接口约定同步更新。

## 1. 一句话概念

玩家从真实城市地铁线网中选择一张图，在限定时间内通过限流、加车、封站、广播等手段，让客流自己涌、自己堵、自己疏解，最终以积分评价经营水平。无限模式持续挑战递增难度。肉鸽机制只改参数，不改规则，涌现本质不变。

---

## 2. 核心体验

- **真实感**：线网来自真实城市，站点名称、换乘关系、线路走向有据可查。
- **涌现感**：乘客自己涌出来，拥堵自己形成，玩家只能改规则。
- **决策感**：限流还是加车？封站还是广播？每个选择都有代价。
- **评价感**：积分量化经营水平，可重复挑战、对比策略。
- **肉鸽感**：每局随机事件和升级，但核心涌现机制不变。
- **视野感**：缩小看整体潮汐，放大看站点细节，点击站点快速定位。
- **时间感**：昼夜交替、天气变化，画面和参数一起变，玩家不看数字就知道“要来了”。

---

## 3. 核心循环

```
观察客流 → 识别压力点 → 做出调度决策 → 系统响应 → 产生新涌现 → 再观察
```

单局时长：5—12 分钟（无限模式除外）。  
失败条件：踩踏风险、全网瘫痪、满意度归零。  
成功条件：安全、准点、吞吐量达标，积分评级。

| -------- | ----------------- | ------- | ------------------ | ---- |

## 5. 难度池详细设计

### 5.1 入门池（★）

**线网特征：** 1—2 条线，5—8 个站，1 个换乘站。  
**真实来源示例：** 哥本哈根 M1/M2、里斯本蓝线、成都 1 号线早期段、杭州 1 号线早期段、曼谷 BTS 素坤逸线、温州 S1/S2。  
**客流特征：** 单峰或双峰，节奏慢，异常少。  
**目标：** 积分 1000 通关，熟悉操作与涌现。  
**典型时长：** 5 分钟。

### 5.2 进阶池（★★）

**线网特征：** 3—5 条线，15—25 个站，3—5 个换乘站。  
**真实来源示例：** 新加坡 MRT 早期线网、香港荃湾线+观塘线+港岛线、台北淡水信义线+板南线、武汉 2+4 号线、成都 1/2/3 号线组合或 6 号线。  
**客流特征：** 明显早晚高峰，换乘压力大，偶发异常。  
**目标：** 8 分钟内准点率与满意度达标，积分 3000。  
**典型时长：** 8 分钟。

### 5.3 硬核池（★★★）

**线网特征：** 8 条线以上，50+ 站，10+ 换乘站，环线+放射线。  
**真实来源示例：** 重庆、北京、上海、东京、伦敦、巴黎、纽约、莫斯科地铁全网。  
**客流特征：** 潮汐流、级联延误、多线耦合、突发大客流。  
**目标：** 12 分钟内尽量不瘫痪，积分 6000。  
**典型时长：** 12 分钟。

### 5.4 无限模式

**线网来源：** 以成都全线为基础，从真实线网随机抽取线路组合，或程序化生成。  
**规则：** 每 3 分钟新增 1 条线或 1 个换乘站，事件频率递增。  
**目标：** 存活尽可能久，积分累积。  
**结束条件：** 全网瘫痪或满意度归零。  
**特色：** 每局线网不同，肉鸽升级每局不同。

## 6. 积分评价体系

### 6.1 基础指标

| 指标   | 说明                   | 权重 |
| ------ | ---------------------- | ---- |
| 准点率 | 列车到达准点比例       | 25%  |
| 满意度 | 乘客平均耐心剩余       | 25%  |
| 吞吐量 | 总运送人数             | 20%  |
| 安全分 | 无踩踏、无恐慌事件     | 20%  |
| 效率分 | 平均等待时间、换乘时间 | 10%  |

### 6.2 积分公式（示例）

```
总分 = 准点率 × 1000 + 满意度 × 1000 + 吞吐量系数 × 800 + 安全分 × 800 + 效率分 × 400
```

### 6.3 评级

| 积分      | 评级 |
| --------- | ---- |
| < 1000    | D    |
| 1000—2999 | C    |
| 3000—4999 | B    |
| 5000—6999 | A    |
| ≥ 7000    | S    |

### 6.4 结算展示

- 积分明细
- 拥堵热力图回放
- 关键时刻标记（最大拥堵、最佳决策、失误点）
- 与历史最佳对比

## 7. 肉鸽机制（不偏离涌现本质）

### 7.1 原则

- 肉鸽只改变**规则和参数**，不直接改变客流结果。
- 玩家不能直接生成或删除乘客。
- 所有随机事件都通过反馈循环影响涌现。

### 7.2 每局随机

- **线网变体**：同一城市不同线路组合。
- **初始事件**：开局随机 1 个正面 + 1 个负面。
- **升级选择**：每 2 分钟三选一。
- **异常事件**：随机时间触发。

### 7.3 升级示例

| 升级     | 效果              | 代价          |
| -------- | ----------------- | ------------- |
| 快速闸机 | 进站速度 +20%     | 满意度 -5%    |
| 智能广播 | 乘客改道概率 +15% | 冷却 +30s     |
| 备用列车 | 加车成本 -30%     | 初始资源 -20% |
| 宽敞站台 | 站台容量 +25%     | 建设时间 +10s |
| 应急通道 | 封站副作用 -50%   | 限流效果 -10% |

### 7.4 随机事件示例

| 事件       | 效果                     |
| ---------- | ------------------------ |
| 演唱会散场 | 某站短时大客流           |
| 暴雨       | 整体需求 +20%，速度 -10% |
| 信号故障   | 某线延误传播             |
| 出口关闭   | 某站容量 -30%            |
| 票价优惠   | 需求 +15%，持续 1 分钟   |
| 设备检修   | 某站闸机 -50%            |

## 8. 游戏对象与玩家操作

### 乘客 Agent

每个乘客只有简单规则：去目的地、选最短路径、避开拥挤、跟人走、耐心有限、从众/恐慌。  
属性：起点、终点、耐心、速度、从众性、信息获取。

### 地铁列车

容量、班次、速度、延误传播。一条线晚点可能波及换乘站。

### 站点

闸机、站台、换乘通道、出入口。每个站点有容量上限和密度阈值。

### 玩家操作

| 操作   | 效果         | 成本       |
| ------ | ------------ | ---------- |
| 限流   | 降低进站速率 | 满意度下降 |
| 加车   | 提升运力     | 资源消耗   |
| 跳站   | 缓解某站压力 | 其他站积压 |
| 封站   | 强制改变人流 | 满意度大降 |
| 广播   | 引导路径选择 | 冷却长     |
| 调班次 | 长期影响需求 | 延迟生效   |

---

## 9. 涌现从哪来

- 乘客避拥挤 → 人流转向 → 新拥堵点。
- 列车延误 → 站台积压 → 换乘通道堵塞 → 级联失效。
- 从众/恐慌 → 局部密度突变 → 踩踏风险。
- 玩家限流 → 站外排队 → 需求转移 → 邻站爆满。
- 时间与天气变化 → 需求结构改变 → 旧策略失效 → 新涌现。

这些都不是脚本，是规则互动的结果。

## 10. 时间变化系统

时间不是背景板，是**涌现的驱动参数**。一局 5—12 分钟映射游戏内一天 24 小时，昼夜、天气、主题氛围同步变化。

### 10.1 昼夜循环

| 现实时长 | 游戏内时间 | 典型场景           |
| -------- | ---------- | ------------------ |
| 1 分钟   | 2 小时     | 早高峰 7:00—9:00   |
| 1 分钟   | 2 小时     | 平峰 9:00—11:00    |
| 1 分钟   | 2 小时     | 午间 11:00—13:00   |
| 1 分钟   | 2 小时     | 晚高峰 17:00—19:00 |
| 1 分钟   | 2 小时     | 夜间 19:00—23:00   |

**视觉表现：**

| 时段         | 背景色           | 线路色 | 乘客颜色       | 整体氛围   |
| ------------ | ---------------- | ------ | -------------- | ---------- |
| 清晨 5—7     | 深蓝紫 #1a1a3e   | 低饱和 | 稀疏，偏绿     | 安静，冷   |
| 早高峰 7—9   | 暖橙渐变 #2e1a1a | 高饱和 | 密集，黄红增多 | 紧张，暖   |
| 平峰 9—11    | 浅灰蓝 #1e2a3e   | 中饱和 | 稀疏，绿       | 平静，中性 |
| 午间 11—13   | 明亮蓝 #1a2a3e   | 中饱和 | 中等，绿黄     | 轻松，亮   |
| 晚高峰 17—19 | 暖红渐变 #3e1a1a | 高饱和 | 密集，红紫     | 高压，热   |
| 夜间 19—23   | 深蓝黑 #0e0e1e   | 低饱和 | 稀疏，暗绿     | 疲惫，冷   |

**过渡方式：** 着色器渐变，每 10 秒微调色温，玩家不会突然发现“天亮了”，但回头一看氛围已变。

**乘客行为随时间变化：**

- 早高峰：目的地集中在商业区/换乘站，耐心低，从众高。
- 平峰：目的地分散，耐心高，从众低。
- 晚高峰：反向潮汐，疲惫值高，恐慌阈值低。
- 夜间：班次减少，乘客少但等车久，满意度下降快。

### 10.2 天气系统

天气直接改参数，与昼夜叠加。

| 天气 | 视觉                     | 参数影响                       | 出现时段 |
| ---- | ------------------------ | ------------------------------ | -------- |
| 晴   | 干净背景，无粒子         | 基准                           | 全天     |
| 阴   | 灰色调，低对比           | 需求 -5%                       | 全天     |
| 小雨 | 细密斜线粒子，地面反光   | 需求 +10%，速度 -5%            | 全天     |
| 暴雨 | 密集粒子，屏幕水痕，雷鸣 | 需求 +20%，速度 -10%，故障率 + | 夏秋     |
| 雪   | 白色粒子，慢速飘落       | 需求 -10%，速度 -15%           | 冬       |
| 雾   | 低透明度，远景模糊       | 速度 -10%，能见度低            | 晨       |

**叠加效果：** 晚高峰 + 暴雨 = 压力翻倍，画面偏红紫，警报频繁。这是“涌”最猛的组合。

### 10.3 主题氛围

**背景元素：**

- **远景云层**：白天薄云，傍晚火烧云，夜间星空/城市灯光。
- **城市剪影**：随昼夜亮灯率变化，早高峰写字楼亮，夜间住宅区亮。
- **地标**：根据所选线路城市，背景出现地标剪影，如重庆的穿楼、跨江大桥，香港的维多利亚港，北京的故宫角楼。
- **线路特征**：重庆的穿楼站点在近景下可以看到楼中站台；跨江段背景出现江面倒影。

**UI 风格：**

- 早高峰：UI 边缘泛暖光，警报色偏橙红。
- 平峰：UI 干净，低饱和。
- 晚高峰：UI 边缘泛红光，按钮冷却环更醒目。
- 夜间：UI 暗色，霓虹描边更亮。

**音效基调：**

- 清晨：稀疏鸟鸣、远处列车声。
- 早高峰：密集脚步声、广播、闸机滴滴。
- 平峰：轻松环境音，偶尔广播。
- 晚高峰：人群嘈杂、警报、心跳。
- 夜间：空旷回声、低频轰鸣、偶尔广播。

### 10.4 时间与涌现的关系

- 早高峰：需求集中，换乘站压力大，容易涌。
- 平峰：需求分散，玩家可以喘口气，调整策略。
- 晚高峰：反向潮汐，之前管用的策略可能失效。
- 夜间：班次少，一辆车晚点影响更大，容错率低。
- 天气叠加：暴雨+晚高峰，系统逼近临界，一次小故障就可能级联。

**玩家感受：** 不用看时钟，光看画面和听声音就知道“要来了”。时间变化本身就是反馈的一部分。

### 10.5 实现方式

**着色器：**

- 全局色调映射：`uniform float time_of_day`，驱动背景色、线路色、UI 色调。
- 天气粒子：GPU 粒子系统，参数由 `WeatherSystem` 控制。
- 背景渐变：全屏 quad，用噪声+渐变生成天空/城市剪影。
- 过渡：所有参数用 `lerp` 平滑，避免突变。

**数据结构：**

```gdscript
# TimeSystem.gd
var game_hour: float = 7.0
var time_speed: float = 2.0  # 游戏内小时/分钟
var weather: String = "clear"
var weather_intensity: float = 0.0

func _process(delta):
    game_hour += time_speed * delta / 60.0
    if game_hour >= 24.0:
        game_hour -= 24.0
    update_visuals()
    update_passenger_params()
```

**接口：**

- `TimeSystem.get_hour()` → 当前游戏内小时
- `TimeSystem.get_period()` → `morning_peak` / `flat` / `evening_peak` / `night`
- `TimeSystem.get_weather()` → 当前天气
- `TimeSystem.get_demand_multiplier()` → 需求乘数
- `TimeSystem.get_speed_multiplier()` → 速度乘数

## 11. 三段式视野与成分云

### 11.1 三段式视野

| 视野层级     | 触发方式       | 画面表现                                         | 玩家用途             |
| ------------ | -------------- | ------------------------------------------------ | -------------------- |
| 远景（云层） | 缩到最小       | 乘客合并为“成分云”，用颜色和密度表示客流构成     | 看全网潮汐、区域压力 |
| 中景（默认） | 默认缩放       | 类似 Mini Metro，乘客为小圆点，线路和站点清晰    | 日常调度、观察拥堵   |
| 近景（站点） | 放大或点击站点 | 可见站点内部细节：闸机、站台、换乘通道、人群流动 | 精细调度、应急决策   |

### 11.2 成分云

- 远景下，大量乘客不再单独渲染，而是合并为半透明色块。
- 颜色表示乘客状态构成：绿=正常、黄=等待、红=拥堵、紫=恐慌。
- 密度越高，云越浓；颜色越偏红紫，压力越大。
- 云会缓慢流动，方向表示人群移动趋势。
- 鼠标悬停或点击云，可以显示该区域客流构成饼图。

### 11.3 缩放与衔接动画

- **PC：** 鼠标滚轮缩放。
- **移动端：** 屏幕右侧上下拖动激活式 UI 缩放。
- **点击站点：** 快速进入该站点近景视野。
- **衔接动画：**
  - 缩小：分散的小圆点逐渐融合，颜色混合，形成成分云。
  - 放大：成分云逐渐分裂，小圆点从云中“析出”，落到具体位置。
  - 过渡用 0.3—0.5 秒缓动，避免突兀。
  - 云与小圆点之间用粒子过渡，颜色渐变。

## 12. 美术风格与着色器

### 12.1 定位

整体类似 Mini Metro：极简几何、干净线条、低饱和背景、高饱和线路。加入三段式视野、成分云和时间变化。

### 12.2 统一规范

- **背景**：随昼夜变化（见 10.1），深灰/深蓝为基底。
- **线路**：高饱和霓虹（青、品红、黄、绿），随昼夜微调饱和度。
- **乘客**：小圆点，颜色表示状态（绿=正常，黄=等待，红=拥堵，紫=恐慌）。
- **站点**：白色圆环，大小表示容量。
- **热力图**：绿→黄→红→白。
- **成分云**：半透明色块，颜色混合，密度表示压力。
- **UI**：半透明深色面板 + 霓虹描边，随昼夜调整亮度。
- **手绘素材**：仅用于图标、Logo、教程插图，风格统一为单色线稿 + 霓虹填充。

### 12.3 着色器实现

- 密度场热力图
- 流线/方向场
- 实例化乘客
- 成分云渲染：低分辨率密度纹理 + 颜色映射 + 模糊
- 粒子过渡：云与小圆点之间的切换
- 全局色调映射：随时间变化
- 天气粒子：雨、雪、雾
- Bloom、色差、径向模糊
- 历史帧反馈（拖尾、潮汐）

### 12.4 音效

- 人群声随密度升高
- 警报、广播、心跳
- 异常触发时音效突变
- 缩放时音效随视野变化：远景低沉，近景清晰
- 时间变化时音效基调改变（见 10.3）

## 13. 技术架构

```
模拟层：乘客 Agent + 列车 + 站点 + 环境规则 + 时间系统
   ↓
预测层（可选）：时间序列模型 → 预测未来客流
   ↓
反馈层：着色器可视化 + UI + 音效 + 事件系统
   ↓
玩家层：限流/加车/封站/广播/升级
   ↓
回到模拟层
```

**新增模块：**

- `TimeSystem.gd`：昼夜循环、天气、时段参数。
- `WeatherSystem.gd`：天气粒子、参数影响。
- `ThemeManager.gd`：背景、UI、音效基调随时间切换。

## 14. 真实线网数据来源

| 来源           | 内容               | 格式        |
| -------------- | ------------------ | ----------- |
| OpenStreetMap  | 线路、站点坐标     | XML/GeoJSON |

## 15. 游戏场景样例阐释

### 场景 1：入门池——温州 S1/S2

一条线，7 个站，无换乘。5 分钟，清晨发车，平峰，晴朗，画面干净。中段进入早高峰，暖色，客流增多，玩家第一次感到“涌”。结尾回到平峰，玩家松口气。玩家操作限流、加车。目标积分 1000。教学重点：理解乘客自己涌、热力图、基本操作。

### 场景 2：进阶池——香港荃湾线 + 观塘线

两条线，18 个站，2 个换乘站（太子、旺角）。8 分钟，晚高峰 + 小雨，画面偏红，地面反光。换乘站压力大，广播引导成为关键。夜间雨停，客流减少，但班次也减少。玩家操作限流、加车、跳站、广播。目标积分 3000。教学重点：换乘压力、级联延误、广播引导。

### 场景 3：硬核池——重庆地铁全网

20+ 条线，50+ 换乘站。12 分钟，早高峰 + 暴雨，穿楼站点近景可见楼中站台，跨江段江面倒影。画面偏红紫，Bloom 频繁，警报不断。夜间转入平峰，但故障遗留，玩家需要收尾。玩家操作全部，多线协同。目标积分 6000，不瘫痪。教学重点：级联失效、多线耦合、资源分配。

### 场景 4：无限模式——随机组合线网

从真实线网随机抽取 2 条线开始，每 3 分钟新增 1 条。无上限，时间循环加速，每 3 分钟过完一天。天气随机，昼夜交替，线网扩展。每 2 分钟随机 1 个事件。玩家操作全部，加肉鸽升级。目标存活尽可能久。教学重点：适应、取舍、长期规划。

### 场景 5：异常爆发——东京 Metro 新宿站

新宿站为核心，多条线交汇。3 分钟短局，夜间 + 演唱会散场 + 暴雨。画面从深蓝黑瞬间转红紫，Bloom 炸开。时间压力极强，玩家必须在 3 分钟内稳住。玩家操作限流、封站、广播、加车。目标避免踩踏，积分 2000。教学重点：应急决策、恐慌传播、从众行为。

## 17. 接口约定

三人并行开发前，先约定以下接口：

- **模拟 → 渲染**：乘客位置、状态、密度场、流场
- **模拟 → UI**：站点密度、列车满载、准点率、满意度
- **UI → 模拟**：玩家操作指令、参数调整
- **事件系统**：异常触发、警报、音效事件
- **视野系统**：当前缩放层级、目标站点、过渡状态
- **时间系统**：当前小时、时段、天气、需求乘数、速度乘数
- **数据格式**：统一用 Godot Resource 或 Dictionary

## 20. 风险与对策

| 风险                 | 对策                                      |
| -------------------- | ----------------------------------------- |
| 真实线网数据整理耗时 | 先做 1—2 个城市，其余用程序化生成         |
| 模拟性能不足         | 低分辨率模拟，GPU 实例化，限制 Agent 数量 |
| 涌现不明显           | 调参：增强反馈循环，提高阈值敏感度        |
| 美术不统一           | 先定色板和线条规范，所有素材按规范        |
| 两周做不完           | 砍内容：先保证入门池可玩，再扩展          |
| 肉鸽偏离涌现         | 升级和事件只改参数，不改规则结构          |
| 双端缩放体验不一致   | 先做 PC，移动端用同一套视野系统，UI 适配  |
| 成分云性能开销       | 用低分辨率密度纹理 + 模糊，GPU 渲染       |
| 时间系统增加复杂度   | 先做昼夜色调，天气后置；接口提前约定      |

## 21. 一句话总结

**真实线网为舞台，三种难度池 + 无限模式，限时经营 + 积分评价，肉鸽只改参数不改规则；乘客自己涌，玩家只调规则，三段式视野从成分云到站点细节，昼夜天气驱动涌现，着色器负责视觉爆发，三人两周并行开发，先跑通入门池再扩展。**
